# Contributing to Solar

Thanks for helping improve Solar.

## Contribution Goals

Solar is an open-source project maintained by Uhorizon AI. We welcome:

- Bug fixes.
- Documentation improvements.
- Reusable framework improvements.
- New ideas discussed through issues before implementation.

## Scope Boundaries

Solar follows strict architecture boundaries:

- `core/` is versioned framework code and documentation.
- `sun/` and `planets/` are user runtime workspaces and are gitignored.
- Contributions in this repository should focus on `core/` and shared files.

Primary references:
- `AGENTS.md`
- `core/AGENTS.md`
- `core/docs/orchestration-blueprint.md`

## Language Policy

- `core/` content must be in English: code, comments, documentation, tests and error codes, without exception.
- End-user messages generated by `core/` (for example gateway `reply_text`) are in English by default. Another language comes from configuration, never from strings hardcoded in `core/`.
- Runtime/planet-specific content can follow user language preferences outside framework scope.

## Before You Start

1. Check if an issue already exists.
2. Open an issue for non-trivial changes.
3. Confirm design alignment before large PRs.

## Branch and Commit Workflow

1. Create a focused branch from `main`.
2. Keep changes small and reviewable.
3. Use clear commit messages describing intent and impact.
4. Update docs/contracts when behavior changes.
5. Update `CHANGELOG.md` for notable framework changes.

## Pull Request Requirements

Each PR should include:

- Problem statement.
- Scope and files changed.
- Behavior impact.
- Validation steps performed.

Checklist:
- [ ] Scope matches Solar boundaries.
- [ ] `core/` updates are in English.
- [ ] No secrets or private user data.
- [ ] Documentation updated when needed.
- [ ] `CHANGELOG.md` updated when relevant.

## Merge Policy

Short rules so that parallel PRs do not break each other:

1. **CI is the single "nothing is broken" gate.** The `Test suite` workflow runs the `core/tests` suite on every PR and on `main`: everything on Ubuntu, and on macOS the pytest files that depend on macOS plus every shell test (on macOS a test that starts the real console is skipped, with the reason printed, only when that start exceeds a 10 s cap; a quick failure still fails). A PR is mergeable only with it green. Reviewers (human or AI) judge design and risk; they do not replace the suite.
2. **One PR at a time.** After each merge, the next PR is rebased on the new `main` and must pass CI again before review is requested.
3. **Review only what changed.** After a rebase or a push, reviewers look only at what changed since their last review, not at the whole diff again.
4. **Merge order follows shared files.** PRs that touch the same hot files (`solar_state.py`, `router.py`, `providers/base.py`, `operations.py`) merge one after another, smallest or most urgent first; unrelated PRs can go in any order.
5. **Releases are grouped.** Publish one release for several merged PRs, except for an urgent fix.

Making the check required for merging is a repository setting (branch protection) and is done by the maintainer.

## Creating a Release

**Maintainers only:** Solar uses semantic versioning for framework releases.

**Release policy.** Releases are grouped: one release per week (the cadence is the maintainer's call), covering every PR merged since the last one. An urgent fix (it breaks users, or security) may go out of cadence. `--publish` refuses unless the `Test suite` checks `Suite (ubuntu-latest)` and `Suite (macos-latest)` are green on the commit under the release commit, also with `--publish --retry`. The only way around it is `--publish --urgent "reason"`, which prints the reason.

To create a release:
```bash
bash core/scripts/create-release.sh [--publish]
```

The script will:
1. Analyze commits since last release (using Conventional Commits)
2. Propose a version bump (MAJOR/MINOR/PATCH)
3. Generate CHANGELOG.md entry
4. Ask for confirmation
5. Create tag and commit locally
6. With `--publish`: check the Test suite is green (or `--urgent "reason"`), run the install E2E, push, create the GitHub Release and verify it

**Commit message format:**
- `feat(scope): description` → MINOR version bump
- `fix(scope): description` → PATCH version bump
- `feat(scope)!: description` or `BREAKING CHANGE:` → MAJOR version bump

See [core/commands/solar-create-release.md](core/commands/solar-create-release.md) for full details.

## Skill and Template Rules

- Add a skill to `core/skills/` only if reusable across domains.
- Keep domain-specific logic out of framework scope.
- Add templates only when they are clearly cross-domain reusable.

## Review Expectations

Maintainers prioritize:

- Correctness and architecture alignment.
- Backward compatibility of contracts.
- Security and privacy safety.
- Clarity of documentation.
